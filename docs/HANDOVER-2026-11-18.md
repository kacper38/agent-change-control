## What a cloud session can do here

Each line was measured in this session. The session ran in the permission mode "auto" of Claude Code on the
web.

1. **The repository's hooks run.** The guard of the session's checkout judged every call; its decision log
   holds the lines.
2. **An ask stops the session.** The harness turns a hook's `ask` into an approval request in the owner's app
   and waits. Second scratch write: asked 22:02:49, closed unanswered at 06:51 when the next message of the
   owner was delivered; the call did not run.
3. **Two asked calls ran, and by the harness's record no person answered.** First scratch write: asked
   21:52:23 and waited. At 21:58:57 the owner's message reached the session from his phone, the same call was
   judged again (`ask`) and ran in the same second. The write of the override: asked 07:25:42, ran 08:10:55,
   in the second in which an event from his app arrived. The harness recorded both as decision `accept`,
   source `config`, reason `mode`. For plan rev 3 this is a finding against the condition of probe 4.1 that
   "an `ask` is not approved on its own". Only the owner can say whether he tapped at those two times; the
   session asked him and has no answer yet.
4. **The harness's own check refused two calls before any prompt**, with the reason "undermining oversight":
   the session's own write of `.claude/guard.local.json` on 2026-11-17, before the owner had said anything
   about it, and a shell call that would have fetched Python 3.9 with `uv`. Neither was retried or done another
   way. `host-install` itself stood down, as its `auto` knob says for a container.
5. **Python.** 3.13 with pytest runs offline through `uv run --offline`. There is no 3.9, so
   `g070/suite-cloud.sh` gives lint, a static check of the 3.9 grammar (`g070/py39_check.py`) and the 3.13
   result. The real 3.9 run is the pull request's CI job.
6. **The tracker does not work.** `tools/tracker/tracker.py show 50` ends with "GitHub GraphQL is not
   available from Claude Code sessions", and `gh auth status` calls the token invalid. The steps
   `tracker.py review` and `tracker.py new` wait for the Mac.
7. **GitHub works through the harness's own tools.** They opened pull request #54 and read its check runs, and
   they can merge. After a subscription to the pull request, CI results arrive in the session as events.
8. **The after-build checks.** `expect.py`, `expect_files.py`, `caps_pairs.py` and `caps_pairs_ref.py` run as
   they are. `heldout_fed.py` got a `delete-guard` ask, because the rule reads the text of a script a command
   names and this one held delete forms as data; since `723374a` its payloads lie in
   `heldout_fed_payloads.json` and it runs. `tools/guard/tests/make_fixtures.py` gets the same ask, so the four
   fixture files of step 11 were written by hand; `test_corpus_matches_generator` compares them byte for byte
   with the generator. The replay needs the Mac.
9. **Before any new kind of call, probe it.** `g080-heldout/orch/hookprobe.py` feeds the hook the event with a
   temporary telemetry folder and prints the verdict. With the override in place and every new kind of call
   probed first, the 433 tool calls of the engineer and the reviewer ran without one ask.
10. **The working directory decides which configuration the hook reads.** The hook takes the nearest
    `.claude/guard.json` above the call's working directory and the `guard.local.json` beside it. The engineer
    ran with the handover checkout as its working directory and edited the worktree by absolute path, so the
    override applied. Since 10:34 the session's own shell sits in the worktree (a `cd` sticks, and the harness
    then says not to go back), where no override lies: from then on `guard-config` asks again for the
    session's own calls.
11. **Agents.** A restart of the session's worker ends agents that run in the background; a finished agent
    can be continued by a message. The agent type `code-reviewer` has no tool to write files, which the review
    brief needs, so the reviewer ran as a general-purpose agent with the model set to `opus` and the role file
    of `agents/code-reviewer.md`. An agent's report comes back through the harness and not as a file;
    `g080-heldout/orch/agent_reports.py` reads the reports out of the agent's transcript.
12. **`bin/fresh-review` runs here.** Two runs, 0.91 and 0.99 USD.

## The build: the owner chose the override

The build is nothing but edits under `tools/guard/`. The session laid out three ways (the Mac, the Mac's
override in the cloud, a tap per edit) and recommended the Mac. The owner chose the override. 140 calls then
ran with the `guard-config` ask silenced: 139 by the engineer and one by the session, the version line. The
pull request's evidence folder lists them one by one.

Not done, on purpose: writing the files through the shell, building under a path the rule does not match, or
using the restart case of point 3. Each would pass the rule this work is about.

What an engineer in a cloud session must be told beside `g080/brief-a.md`:

- `<REPO>` is the checkout, `WT` is `<REPO>/.claude/worktrees/g080-a`, `<SCRATCH>` is a copy of `g080/` and
  `g070/` outside the checkout (the brief forbids temporary files in a checkout; never a copy of
  `g080-heldout/`).
- A call the guard asks about stops the whole session until the owner answers. No delete or force-push words
  on a command line (the brief's rule 5), and no script run by name whose own text holds such words: the
  candidate commands stay in a data file the script reads.
- The working directory stays the checkout that holds the override; the worktree is reached by absolute path
  or `git -C`.
- Only Python 3.13 runs. The brief's rules for 3.9 stay; the 3.9 run happens on the Mac or in CI.
- The cloud harness has a stop hook that reports untracked files; `.claude/worktrees/` is one. Nothing is to
  be committed for it.
