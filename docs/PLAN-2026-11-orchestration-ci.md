## 0. What the request means (two readings, both in scope)

1. **Orchestrated work flows through CI.** One session plans and splits the work; each worker produces a branch and a pull request; the same `ci` check runs on every PR however the session was configured; a person approves. This is the talk's model.
2. **The orchestration itself runs headless in CI.** A saved workflow is started by `claude -p` or the GitHub Action inside a job.

Phases 1 and 2 deliver reading 1 and the read-only part of reading 2 (review). An agent that writes code from inside CI is below the cut line (section 8).

Rev 3 adds a third request, made on 2026-11-15 after the second research round: a repository that holds nothing secret should use everything available (cloud workers, no fixed agent count, reviewers from more than one vendor, agents merging low-risk changes), while client and secret repositories keep the plan as approved. D11 turns that into two modes, and Phase 4 delivers the open one.

What this plan does NOT do: in strict mode it adopts no cloud feature (section 2, facts 11–12); in open mode it adopts cloud sessions started with `claude --cloud`, if probe 4.1 allows them (D12), and nothing else from that family (no Projects, Code Review, routines or agent teams; fact 18); it does not install `pstack` (fact 16); it does not make a model review a merge gate, except a verifier's verdict for one narrow class in open mode after a trial (D14); it does not port the CI jobs to Azure Pipelines yet.

## 2. Verified facts that shape the design (surprises first)

1. **A workflow is flat.** Agents started by a workflow script have no spawn tool, for the default agent type and for `general-purpose` (**T**, from the agents' own tool lists). The script may call one child workflow, one level deep (**D**). Real nesting exists only through the `Agent` tool.
2. **A CI job can go green having done nothing.** `claude-code-action` stops reading at the first result message while background subagents are still running; action issues #1499, #1852 and #1646 are open with no maintainer reply (**V**). The community mitigation is `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` (**V** that it is documented and reported to work; one report says it must go through the action's `settings` input because a step-level `env:` did not reach the CLI, **R**).
3. **The exit code does not report a denial.** A saved workflow that was denied at launch still exits `0` with `subtype: success`; the denial appears only in `permission_denials` of the JSON output (**T**). Inside a workflow, a failed agent resolves to `null` rather than failing the run (**D**).
4. **Starting a saved workflow by name works headless.** `claude -p "/<name>" --permission-mode dontAsk --allowedTools "Workflow(<name>)"` runs `.claude/workflows/<name>.js`; without the rule the launch is denied (**T**). GitHub's own `gh-aw` does the same with a bare `Workflow` rule and keeps the feature off by default (**V**); 3 of its last 8 smoke runs failed, cause not established (**V** for the count).
5. **Settings hooks fire where they must.** A `PreToolUse` hook from project `.claude/settings.json` ran inside a workflow agent (`agent_type: workflow-subagent`) and its exit 2 blocked the call (**T**); the docs say the same for subagents (**V**). Hooks in agent frontmatter are skipped in `-p` runs (**V**), and issues report them not firing in other paths (**R**).
6. **Hooks fail open on timeout unless told otherwise.** `onFailure: "block"` makes a timeout or crash block the call; it needs 2.1.295 or later (**D**). Copilot has no equivalent: its hook timeouts always fail open (**V**).
7. **On a pull request, the action restores `.claude/` from the base branch but leaves the rest at PR head** (**D**). The kit's hook command is `python3 "$CLAUDE_PROJECT_DIR"/tools/guard/guard.py`, a repo-relative script, so in a PR-triggered job the PR supplies the guard (**I**). Structural controls have to carry such a job; the hook is a second line.
8. **Nesting depth is a moving default.** Off in 2.1.217–2.1.218, three layers from 2.1.219 (**V**). One hardening repo says the default arrives by remote flag and pins it (**R**). `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` pins it (**D**).
9. **`--max-budget-usd` is the only enforced spend cap (rev 3: reworded, it is not a hard one).** It stops background subagents too (**V**). The 200-spawns-per-session cap was removed in 2.1.224 (**V**). Users report runaway workflow runs, one of about $606 (**R**). Rev 3 correction: the cap is checked against Claude Code's own client-side estimate, and "Spend can pass the cap, so leave headroom" (**V**, `cli-reference`, 2026-11-15).
10. **The action defaults to auto permission mode**, which its own docs call "a review, not a boundary" (**D**). A strict allowlist needs an explicit `--permission-mode`. Plain `claude -p` starts in Manual mode since 2.1.302 (**D**). `--bare` skips hooks and is announced as the future default for `-p` (**D**), so flags must be explicit.
11. **Agent teams do not run headless**: no teammates are spawned in `-p` or SDK sessions (**D**).
12. **Cloud features leave the boundary.** Projects, Code Review, ultrareview, routines and PR auto-fix run on Anthropic infrastructure and are unavailable on Bedrock or Foundry; self-hosted environments still send the transcript to Anthropic (**D**). The in-boundary path is the action or `claude -p` on our own runner with Bedrock or Foundry through OIDC.
13. **`agent-approval-check` detects agent work by committer e-mail or PR creator login, not by the `Co-Authored-By` trailer**, and the PR author's `/approve <head-sha>` comment counts as one approval (**D**, source read 2026-11-13). Local sessions commit under the owner's identity, so today the check would report "no agent activity" (**I**). Rev 3 precision, from the source at `9fa68854da5f` (**D**, 2026-11-15): a valid approval is a non-dismissed APPROVED review or an `/approve <head-sha>` comment "from non-agent users with write access"; reviews and comments from agent identities do not count; the script must run from the default branch, "via pull_request_target, issue_comment, or workflow_run triggers". Detection reads two inputs: `agent_emails`, matched against the committer e-mail of each commit, and `agent_app_logins`, matched against the login that created the PR. With neither present the check posts success with "No agent activity". A committer e-mail is whatever the committing session sets.
14. **Copilot limits.** VS Code subagents do not nest unless `chat.subagents.allowInvocationsFromSubagents` is on, depth at most five; the harness that supports nesting and handoffs is deprecated with removal announced for February 2027; a worker model above the main model's cost tier does not run; the cloud agent ignores handoffs (**V**). No dynamic workflows exist there.
15. **What the docs now say to stop doing**: using subagents to protect context or to get a better answer, emphasis in capitals, "keep going" prompts, describing the file layout in the instructions file (**D**). The cost guardrails already in use (brief first, distinct lenses, five agents) match this.

On a public repository any commenter's text may become an input (**I**).

22. **A session can merge today.** The guard allows `gh pr merge` (an `allow` fixture covers it, **T**, 2026-11-15) and the ruleset on `main` requires `ci` with 0 approvals (section 1), so only the working agreement stops a session from merging a green PR. Step 2.2 closes this on the server.
23. **How the guard reads its configuration today.** `rules_off` is honoured only when the `.claude/guard.json` in the working tree beside `.git` says `boundary: own`; the file is not read from git, so an uncommitted edit counts. A listed rule still runs and is logged as skipped; only its `ask` is silenced, and a `deny` stands. `guard.local.json` sets only `rules_off`, and `KZ_RULES_OFF` does the same for one shell. In `guard.py` `KZ_BOUNDARY` replaces the boundary in either direction, so `KZ_BOUNDARY=own` switches `egress-guard` off in a repository whose file says `client`; only the egress screen takes that variable as tighten-only (**V**, `guard.py:159-200` and `:1144`, `egress_screen.py:87-89`, read 2026-11-15). The asks of `deploy-ask` and `delete-guard` can be silenced this way in an own repository, as approved on 2026-11-01 (**V**, `tools/guard/tests/test_rules_off.py`).
24. **A new target starts with this repository's boundary.** `.claude/guard.json` is an `init` entry with no template of its own, so `install.sh` copies this repository's file, which says `boundary: own`, into every new target, and no flag chooses otherwise (**V**, `kit.manifest:13`, `install.sh:90`, `.claude/guard.json:5`, read 2026-11-15). A client repository therefore honours `rules_off` and skips the egress hold until someone edits the line.
25. **What a required check on GitHub can and cannot pin.** `agent-approval-check` posts a commit status from a workflow that runs on `pull_request_target` and `issue_comment`, from the default branch, with no checkout (**D**, the action's example, re-read 2026-11-15). A ruleset on a repository owned by a personal account can pin a required check to its source app, not to a workflow, and every workflow posts as GitHub Actions, so a pull request that adds a workflow with `statuses: write` can post the same check name on its own head; the action's source says "An actor who can push workflow changes to the default branch can spoof any required status check, including this one" (**V**). Environment rules evaluate against `refs/pull/<n>/merge` for `pull_request` and against the default branch for `pull_request_target` (**V**, GitHub changelog 2025-11-07). From 2026-12-02 GitHub blocks `pull_request_target` by default in public repositories unless an Actions event policy allows it; private repositories are not affected (**V**, GitHub changelog 2026-11-02, re-read 2026-11-15). Such a policy can be created in a repository, an organisation or an enterprise and can be scoped to single workflow paths (**D**, GitHub docs, 2026-11-15); the docs do not say whether a repository owned by a personal account can create one. An event caused by a job's own `GITHUB_TOKEN` starts no new workflow run, apart from `workflow_dispatch` and `repository_dispatch` (**D**, GitHub docs, 2026-11-15), so a merge made with that token starts no run on `main`. A pull request's file listing returns at most 3000 files and marks renamed and removed entries, with the old path in `previous_filename` (**V**).

## 3. Design decisions (recommendation; the alternative is named)

**D1 — Three levels, depth pinned at two.**
- Level 0, the orchestrator: the interactive session on Fable. It plans, writes the brief, splits the work into packets (one packet = one tracker item = one branch = one PR) and reads results. It does not merge (rev 3: in open mode a required check may merge one narrow class, D14; no agent decides a merge in either mode).
- Level 1, workers: the Opus engineer agents, one packet each, each in its own worktree. A worker returns a structured result: branch, checks run with exit codes, open risks.
- Rev 3: the brief names the evidence that will prove the packet done (a command and its expected result), the paths the worker may write and those it may not, and the actions it may not take. The result is data, checked by `assert_run.py` (step 2.3): the branch, a head commit equal to the branch tip, each check with its exit code, and a list of what was not verified. A missing result is a gap, never a pass. The first packet goes end to end before the others start.
- Level 2, sub-workers: read-only helpers a worker may start (a search, one verifier). They never write.
- Alternative: keep the default depth of three. Rejected: each layer multiplies tokens and nobody reads level-3 output.

**D2 — The shape follows the job.**

| Job | Mechanism |
|---|---|
| packets with a person present | `Agent` fan-out from the session, with a written brief; up to five without asking, as the guard works today; bounded by the run budget in open mode (D13) |
| repeatable, or headless | a saved workflow; it is flat, so its verify stage replaces level 2 |
| many packets, open mode (rev 3) | cloud sessions started with `claude --cloud`, one packet each, if probe 4.1 allows them (D12); Projects stay outside the kit, because a Projects thread reads no repository hooks (fact 18) |
| strict mode: a client or secret repository, any size | never a cloud feature; own runner with Bedrock or Foundry |

**D3 — Stage gates are separate runs.** A workflow takes no input mid-run, so each stage is its own run and the human decision sits between them in the tracker or the PR: plan → approval → implement → `ci` → review → approval → merge.

**D4 — One contract for every headless Claude job** (the consequence of facts 2, 3, 9 and 10):
1. explicit `--permission-mode dontAsk` with narrow allow rules, including `Workflow(<name>)` for exactly the workflows the job may start. Alternative: auto mode plus an egress-firewall runner, which is what `anthropics/claude-code` enforces in its own CI (**R**); rejected here because an allowlist is deterministic and auditable.
2. `--max-budget-usd`, `--max-turns` as a runaway backstop, a job timeout and a concurrency group.
3. background tasks disabled through the `settings` input.
4. `--json-schema` output, and a deterministic post-step that fails the job on missing structured output, a non-empty `permission_denials`, a `null` stage result or outstanding background tasks. The exit code is not evidence.
5. a read-only job token for review jobs and the action pinned to a commit SHA. Model access through OIDC with no stored key is the target, and the rule for client repos; own repos use a subscription token for now (Q1).
6. a receipt (verdict, head SHA, model, cost, versions) uploaded with an explicit retention.
7. rev 3: the title, body and comments of a pull request are data. A job passes them to the model in a file and never puts them into a shell command.

**D5 — Model review in CI stays advisory and scales with risk.** The single-call `fresh-review` remains the default (existing decision). A panel workflow (the three existing reviewer agents as lenses plus one batched verifier, four agents) runs only on a label. The gates are `ci` and the human approval. Alternative: panel on every PR; rejected on cost (section 11) and on the existing $20-a-month trigger. Rev 3: each finding states its evidence, as a command that was run, a quoted line, or an inference; the verifier re-checks the first two kinds; a finding it could not confirm is listed and counted, not dropped. A lens from another model family may join the panel (D15).

**D6 — The human approval becomes a required check.** `agent-approval-check` with `required_approvals: 1`: on a solo repo the owner's `/approve <head-sha>` is a recorded approval bound to the exact commit. Agent commits are detectable because agent sessions commit and push as a GitHub App (Q2). Rev 3: this is the whole of strict mode; open mode wraps it in the `merge-gate` check of D14. The check counts a review or an `/approve <head-sha>` from a non-agent user with write access and ignores agent identities (fact 13), so an approval posted with the App's token does not count. A session must not be able to post one as the owner. Two lines stand against that: inside a session `gh` and `git` run with the App's token (step 2.1), and the guard denies an `/approve` comment, a PR review and a read of the owner's stored GitHub credentials from a session (steps 1.7 and 2.2). Residual, named: the owner's own `gh` token and git credentials stay on the machine where local sessions run, and a guard that matches command text can be evaded, so an approval by the owner's login is only as strong as keeping those credentials out of a session's reach. Detection has the same shape: it rests on the committer e-mail, which a session sets itself, and on the login that opened the PR (fact 13). A PR that a session opens is marked by the App's login whatever the e-mail says; a session commit that carries the owner's e-mail, in a PR the owner opened by hand, passes as human work. The guard denies a commit under another identity from a session (step 2.1), with the same limit, and opening no PR by hand for a branch a session pushed is a judgment row in `docs/RULES.md`. All of this holds in both modes, and for rev 2 as approved. The structural fix is a session that runs without them (a sandbox, a container or a separate OS user); it is deferred with a trigger (section 5).

**D7 — The guard learns about workflows.** `Workflow` joins the `PreToolUse` matcher: the launch is logged; a name listed in `.claude/guard.json` is allowed; an inline script or an unknown name gets `ask` (which is a denial in a `dontAsk` job). Workflow agents count toward the fan-out total. `.claude/workflows/**` joins the paths where an edit asks. The guard hook gets `onFailure: "block"`.

**D11 — Two modes, chosen per repository, strict by default.**
- The switch is `mode` in `.claude/guard.json`: `strict`, which is also the meaning of a missing key, or `open`.
- `open` is honoured only when the file committed on the default branch, as last fetched from the remote, says `mode: open` together with `boundary: own`. The guard reads that blob with `git show`, with no network call. When it cannot be read, or the working tree differs from it in either key, the repository counts as strict and the difference is logged (step 4.2). Today the guard reads the working-tree file, which an uncommitted edit can change (fact 23).
- `guard.local.json` and the environment cannot open a repository. `KZ_MODE=strict` and `KZ_BOUNDARY=client` tighten, and step 1.7 makes `KZ_BOUNDARY` tighten-only in the guard, as it already is in the egress screen.
- What this stops and what it does not. The guard reads local refs and objects, and the guard itself is a file in the working tree; a session with a shell can rewrite both. So the default-branch read stops a mistaken or drifting edit and any session that keeps to its tools, and it does not stop a session that rewrites refs or the guard. Step 4.2 reads with `--no-replace-objects`, and step 1.7 has the guard deny or ask on the commands that rewrite what it reads (`git update-ref` on remote-tracking refs, `git replace`, `git remote set-url`) and on shell writes to its own files. That raises the cost and logs the commands it matches, no more: an equivalent rewrite (`git fetch . <sha>:refs/remotes/origin/main`, a direct write under `.git/`) matches nothing and leaves no trace. For a client repository the protection against a cloud upload therefore also rests on the judgment controls of D12, and the structural fix is the one named in D6.
- Strict mode is this plan as approved in rev 2 plus the five controls of rev 3 and the hardening of steps 1.7 and 1.8. It is for client repositories, data under NDA, regulated systems, and any own repository that holds something secret. `mode: strict` alone does not turn on the egress hold; `boundary: client` does, so an own repository with something secret in it should say `client` as well.
- Open mode adds D12–D15, for own repositories with nothing secret in them. A repository is opened only after a secret scan of its full history, with the report recorded (D12). Open mode exists on GitHub only; a repository on Azure Repos stays strict.
- The same in both modes: every change passes `ci`; secrets stay in a vault; force-push is denied by `git-guard`, and a deny cannot be switched off; in a cloud session every `ask` is a `deny` and `rules_off` is ignored (step 1.7; D13 names the one exception); in a headless job under `dontAsk` an `ask` is already a denial (D7).
- Deploys and deletions ask the owner (`deploy-ask`, `delete-guard`). In an own repository he can silence an ask through `rules_off`, as approved on 2026-11-01 (fact 23). Under `mode: open` those two rules and `guard-config` may not be listed, because an open repository runs agents with nobody watching.
- Attribution, the same in both modes: agent work is attributable through the agent identity (Q2). The `Co-Authored-By` trailer stays on every agent commit in strict mode. In open mode it may be dropped only on a commit whose author is the GitHub App (step 2.1); every other agent commit keeps it, cloud-session commits included. Hiding that an agent wrote a change is not done in either mode.
- The installer writes `boundary: client` into a new target unless `--boundary own` is given (step 1.8), and `mode: strict` once the key exists (step 4.2). Today it copies this repository's file, `boundary: own` included (fact 24), so until step 1.8 a client repository gets the right boundary only by a hand edit. This changes the installer's default (Q13).
- Why a key of its own, when the proposal of 2026-11-15 named `boundary` as the switch: `boundary` says whose data a repository holds, and an own repository can still be secret; and the guard's default `boundary` is `own`, so a mode read from it would make open the default.
- Alternative: one mode with a switch per feature. Rejected: the owner and an auditor need one reviewed line that says which regime a repository is under.
- Alternative, proposed by the review: refuse `deploy-ask` and `delete-guard` in `rules_off` in every mode. Not taken: it would take back, for strict own repositories, the knob approved on 2026-11-01 (Q14).

**D12 — Cloud workers, open mode only, and only if probe 4.1 allows them.**
- A worker may be a cloud session started with `claude --cloud "<task>"`: one packet = one cloud session = one branch = one PR. The branch is pushed first, because the session clones from GitHub. The brief travels in the task text.
- Only sessions on one repository, the shape that reads the repository's hooks and permission rules (fact 18). Projects threads and sessions over several repositories are not used.
- A cloud session receives the whole repository and its history, unscreened. So a repository is opened only after a secret scan of its full history (`gitleaks`), with the report recorded, and the vendor's retention and training terms for cloud sessions are quoted in `DECISIONS.md` before step 4.3.
- What carries it, since the proxy does not restrict branches (fact 19): the ruleset on `main` with the required checks of step 2.2, which is why cloud workers need that step; the guard hook inside the session, which recognises a cloud session by `CLAUDE_CODE_REMOTE=true`, turns every `ask` into a `deny`, ignores `rules_off` and denies `gh pr merge` (step 1.7); the default network access level; no secrets in the cloud environment.
- Identity decides whether cloud workers are used at all. The owner's approval is a comment by his GitHub account (D6), and Auto-fix already replies under that account (fact 19). If probe 4.1 shows that a cloud session commits, opens a PR, comments or reviews as the owner, or can push a workflow file, cloud workers wait until approvals come from a path no worker can use. If it shows that the session can read, clone or push a repository other than its own, they wait until the connection reaches open repositories only. If it shows a separate identity, that identity goes on the agent lists of `agent-approval-check` and `merge-gate`.
- The `Co-Authored-By` trailer is mandatory on cloud commits. It is a marker and not a control, since the session writes it itself.
- The result is checked like a local worker's, from the branch and the PR, not from the session's summary. It names the session id (`CLAUDE_CODE_REMOTE_SESSION_ID`), so the PR links to the run that produced it.
- A guard rule, `cloud-launch` (step 1.7), denies every way a session can start cloud work: the shell command (`claude --cloud`, its deprecated alias `--remote`, `/autofix-pr`) and the tools (`Agent` with `isolation: remote`, the `schedule` skill). Under `mode: open` step 4.2 lets through one thing only, `claude --cloud "<task>"` started from a local session; the tools, `/autofix-pr` and every launch from inside a cloud session stay denied in every mode, so a worker cannot start routines, Auto-fix or more workers. It has to be a rule and not a sentence, because the command uploads the local repository, with the history of all branches, when the Claude GitHub App is not installed on it (fact 18).
- The cloud session runs the hooks and the guard of the branch it clones, and the launching session pushed that branch. So the launch is allowed only when the hook configuration and every script a hook runs are, on the pushed branch, equal to the default branch's (step 4.2). In this repository that is `.claude/`, `.github/hooks/` and the whole of `tools/`, because the hooks also run the test guard, the tag scan, the ledger, the tracker and the memory store from there. Inside the session the guard is still a file the session can reach, so the required checks of step 2.2 are the boundary and the guard is the second line, as fact 7 says of a CI job.
- That rule stops launches issued by an agent, nothing else. A person typing the command, a session started from the web or the phone, and what the vendor's connection can reach are judgment controls, listed as such in `docs/RULES.md` (step 1.6). GitHub is connected through the Claude GitHub App, installed on open repositories only and never on a client or strict repository; the one exception is the scratch repository of probe 4.1, which holds nothing secret and loses the App again after the probe. `/web-setup` is not used while the machine's `gh` token reaches any strict repository, own or client, because a cloud session may then reach every repository that token can (fact 18; probe 4.1 asks). Where an organisation exists, its `allow_remote_sessions` policy is off.
- Auto-fix stays off while the owner's approval is a comment, because it comments as the owner (fact 19).
- All of this is **D** or **I** until probe 4.1. If the hook does not fire there, an `ask` is approved on its own, or the session can reach a repository other than its own, cloud workers wait.
- Alternative: parallel workers on own runners with `claude -p`. That stays the strict-mode route; in open mode a cloud session needs no runner.

**D13 — A budget instead of a head count, open mode only.**
- Strict mode keeps the ask at the sixth spawn as the guard gives it today, which includes the owner's option to silence it in an own repository through `rules_off` (fact 23).
- In open mode `fan-out` is expected in `rules_off`, and it is the one entry that is also honoured in a cloud session (step 4.2). The rule goes on logging every spawn.
- The limit becomes money. `run_budget_usd` in `guard.json` is passed as `--max-budget-usd` to every headless run the procedure starts. That flag is the only enforced cap, and it is checked against Claude Code's own estimate, so a run can pass it (fact 9); the figure is therefore set with headroom. The ledger flags a session whose measured cost passes the line (step 0.2).
- There is no hard cap inside an interactive session (**D**: `--max-budget-usd` is a print-mode flag), so the line there is a report after the fact, and on a subscription the real bound is the plan's limits. With API billing this decision is revisited before open mode is used.
- The depth stays pinned at two in both modes.
- Alternative: a higher fixed count. Rejected: a head count is a poor proxy, since ten small lookups cost less than one large worker.

**D14 — A verifier that is not the author, then merge for one narrow class, open mode only.**
- Every agent-authored PR gets a verdict for its head SHA from a run that did not write the change: `pass`, `fail`, or `gap` when something could not be run. A new push needs a new verdict. A gap is not a pass.
- The verifier is the same model family as the author. What makes it a check is a fresh context, no tools, evidence it did not choose and a verdict bound to one commit. It is not an independent opinion, and its worth is what the trial below shows.
- Two workflows, because no single trigger is safe for both halves (fact 25). The evidence runs on `pull_request` with `contents: read`, no environment and no secret; its commands are fixed per path class in a file on the base branch and are never taken from the brief or the PR. The verdict runs in `claude-verify.yml` on `workflow_run`, from the default branch, in the environment that holds the model token; that environment accepts `main` only, so no run that a pull request's own files started can read the secret. The verdict job starts only for a PR from a branch of this repository, so a PR from a fork costs no model tokens, gets no verdict and cannot merge by class.
- The evidence is untrusted data. The verdict job downloads the artifact by the id of the run that triggered it, into a directory outside the workspace, and never executes it. Exit codes come from that run's step conclusions through the API. The model gets no tools, and only its schema output counts, bound to `workflow_run.head_sha`. A PR that changes a workflow or the evidence file gets `gap`.
- A test file is code. Once merged it runs in CI and on the owner's machine, and inside the evidence job it can end the test run early with a clean exit or patch what other tests import. So a `pass` also needs the diff to show nothing but tests, which is the model's judgment. The trial measures that judgment on honest changes; it does not measure an author who writes for the verifier, and the classifier's rules and the samples are what stand against that one.
- Trial: for the first 20 agent-authored changes the owner still approves each one, and the verdict is recorded next to his decision. A miss is a head the verifier passed and the owner rejected, or a defect later traced to a passed change. The trial is bound to one verifier model and version, named in every verdict receipt; a change of either restarts the count at 0 of 20. The verdict job needs a model reachable from CI, so a reviewer on the owner's machine (D15) is a panel lens and not the verifier.
- After 20 changes with no miss the owner switches the class on. The switch is a line in the class file on the base branch, changed by a PR he approves, with a `DECISIONS.md` line. No repository variable is involved, so the change is in git history.
- The class is defined per repository in that file. First version, in the class: a new file named `test_*.py` inside an existing `tests/` directory; new test functions added to an existing `test_*.py`, with no existing line changed or removed; a change to an existing prose file under `docs/` that is not named below. In a test file every added line must belong to a new top-level `def test_*` that has no decorator and a name not yet used in the module, or to an import that binds no name the module already has. A line added inside an existing function, a decorator, a `pytestmark`, a fixture, a skip marker, any other module-level statement, a rebinding import or a redefined test name puts the PR outside the class, because each of these can switch an existing test off without removing a line. The rule narrows that and does not end it: the body of a new test still runs as code, so it can end the run early or change what later tests see, and that is what the verdict and the samples are for. Never in the class: `AGENTS.md`, `CLAUDE.md`, `DECISIONS.md`, `README.md`, plan files, `docs/RULES.md`, `docs/SYSTEM.md`, `docs/USING-AT-WORK.md`, skills, agents, anything the `guard-config` rule covers, anything `kit.manifest` installs into a task repository, CI, IaC, any `conftest.py` or `__init__.py`, any pytest, ruff or `pyproject` configuration, and any other new file.
- In this repository no file under `docs/` qualifies today, so the class is new test functions, and none of the last 60 changes on `main` would have met it (**T**, first-parent commits, 2026-11-15). Two of the 60 only added lines to test files, and both fall outside: one extends the body of an existing test, the other puts a skip marker on one. "Docs and tests" read widely would have covered 9 of 60. The class is close to empty here by nature, because in this repository tests travel in the commit of the code they cover and most documents are instructions or controls. It is set per repository, and it is other open repositories that it is for. That is narrower than what was accepted on 2026-11-15 (Q10). The reasons: weakening a test is how a gate gets bypassed; instruction and control documents steer the agents and inform the auditors; a `conftest.py` changes what every other test does.
- The classifier reads the changed files through the API and checks `previous_filename` as well as `filename`. A removed or renamed entry that leaves a protected path, a truncated or incomplete listing, or an entry with no `patch` puts the PR outside the class (fact 25).
- Mechanism: a required check, `merge-gate`, computed by a workflow that runs from the base branch and reads the PR through the API without checking out its code. It passes in one of two ways. By approval: the owner's `/approve <head-sha>`, or his review whose `commit_id` is the head SHA; a "no agent activity" result of `agent-approval-check` never counts here, so in an open repository the owner's own PRs need his `/approve` too. By class: the class is switched on, every changed path is in it, `ci` is green and the verdict for this head SHA is `pass`; then the gate itself merges the PR through the API at the SHA it judged, so a head that moved is not merged.
- No agent decides a merge. The gate merges what passes by class, and the repository's "Allow auto-merge" setting stays off. In a cloud session `gh pr merge` is denied (step 1.7). A local session is not meant to merge either; that is a working-agreement rule, a judgment row in `docs/RULES.md`, and after step 2.2 such a merge can only merge what the required checks already allow.
- What the gate rests on (fact 25): a required check on a personal repository is pinned to its source app and not to a workflow, so the gate holds only while no agent identity can add a workflow or post a status. Three things carry that: the App's permission set (step 2.1), the guard's ask on `.github/workflows/**` (step 1.7), and probe 4.1 for a cloud session's identity. The ruleset pins `ci`, `agent-approval-check` and `merge-gate` to the GitHub Actions source.
- After the switch the owner reads a sample of 1 in 5 of the changes merged through the class, within a week, chosen by the report and not by the agents, and records each on the merged PR with a comment by his account, which the guard denies to a session as it does `/approve`; like the approval, the record is only as strong as keeping his credentials out of a session (D6). One miss turns the class off until the cause has a check (step 1.6). A month with merges in the class and no recorded sample turns it off as well. The gate enforces both.
- Two lines of rev 2 change for an open repository (Q15). The ruleset's own required approvals go back from 1 to 0 there, because `merge-gate` carries the approval; that reverses step 2.2 for open repositories only. And the Q1 deviation widens: a second job, the verdict, uses the token environment, and it runs without a label on agent PRs from branches of the same repository.
- Alternative: the agent that owns the PR merges on the verifier's word, as `pstack` does. Rejected: `pstack` itself says "Never give or bypass an approval the forge enforces", so what changes is the forge's check, not the agent's behaviour.
- Alternative for the gate: a status posted by a second App whose key only a `main`-only environment holds, or an organisation ruleset that requires a named workflow. Deferred with a trigger (section 5).

## 6. Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| Depth 2, not 3 | bounded tokens, every output has a reader | a worker cannot hand a sub-task to a helper that delegates again |
| Flat workflow with a scripted verify stage | the plan is a reviewed file; same script locally and in CI | no ad-hoc delegation inside a run |
| `dontAsk` allowlist, not auto mode | deterministic, auditable, no classifier in the control path | every new tool need is a config change |
| Panel on a label | cost stays under the existing trigger | a risky PR without the label gets the single-lens review only |
| GitHub App as the agent identity | short-lived tokens, a real bot author in every harness, one required approval becomes possible | owner setup; a private key to protect and rotate; a token helper to maintain |
| Subscription token in CI for now | no extra money | a long-lived secret tied to one person's plan; runs draw on the plan's limits |
| The action, not raw `claude -p` | base-branch restore of `.claude/`, actor checks, federation built in | less control over the CLI version and the output format |
| Rev 3: two modes, strict by default | a repository opens only by a reviewed line on its default branch, and a new target starts as `client` and strict | one more key to explain; two regimes to test; an own repository needs the installer flag once |
| Rev 3: cloud workers through `claude --cloud` | parallel packets with no runner to keep, and the repository's guard hook still loads | whether they can be used at all depends on the identity probe 4.1 finds; the whole history goes to the vendor; cost is invisible to the local ledger; the plan's limits drain faster |
| Rev 3: a budget instead of a head count (open) | cheap fan-outs are not interrupted | no hard cap inside an interactive session, only a report afterwards; the headless cap can be passed |
| Rev 3: a merge gate on a verifier's verdict for one narrow class | the owner stops reading additive-test PRs | in this repository none of the last 60 changes would have qualified, so the gain is in other open repositories; a wrong `pass` merges unseen, and a merged test is code that later runs in CI and on the owner's machine; held down by the narrow class, the trial, the samples and the switch-off after one miss |
| Rev 3: the local model as the first second reviewer | no egress, no extra cost, allowed in strict mode | weaker reviews of unmeasured quality; the model's memory while it runs |
| Rev 3 (review): no agent identity may push a workflow or post a status | the required checks cannot be forged by the agent they judge | the owner pushes every CI change himself |
| Rev 3 (review): the installer writes `boundary: client` by default | a client repository starts closed without anyone remembering to close it | an own repository needs `--boundary own` at install |
| Rev 3 (second check): the owner approves from the machine the agents run on | no second device or account in the loop | his approval is only as strong as keeping his credentials out of a session; a named residual until sessions run without them |

## 9. What an auditor gains (and does not)

- Gains: an approval bound to a commit SHA for every agent-authored PR; a receipt per model review (verdict, SHA, model, cost, versions) with a retention; a spawn log that includes workflow agents; orchestration scripts under version control and under the guard's edit rule; a dated record of which tool behaviours were tested on which version.
- Does not gain: assurance that a model review is correct (it stays advisory); a hard control under Copilot (hook timeouts fail open there); a sandbox (the allowlist and the read-only token limit the job, they do not isolate it).
- Rev 3 gains: a table of which rule is enforced by what; a failing check when the controls change without a decision line; one committed line per repository that says which regime it is under; in open mode a verdict receipt per head SHA and a merge record that names the gate's inputs.
- Rev 3 qualifier to the first gain above: an approval bound to a commit SHA exists for every agent-authored PR in strict mode, and in open mode outside the merge class. Inside the class the record is the gate's inputs (verdict receipt, class file version, `ci` run) and the owner's samples.
- Rev 3 qualifier to "does not gain": for the merge class in open mode a model's verdict is no longer advisory, and nothing assures that it is correct beyond the trial and the samples. And in both modes an approval by the owner's login proves his approval only while his credentials stay out of a session's reach (D6).
- Rev 3 does not gain: a record of what a cloud session did beyond its branch, its PR and what the vendor shows, because the local ledger, the spawn log and the guard's decision log (`decisions.jsonl`) do not see it; a technical stop for a person who starts a cloud session by hand in a client checkout, which stays a judgment control; a required check that someone able to push workflow files could not forge. Open mode is not for regulated work.
