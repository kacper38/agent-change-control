## 4. The fourteen patterns, and the other differences between the two engines

Read at `f64c875`; step 3.3's brief reads each use again, and guard 0.13.0 may add some. Three ways to carry one over.

- **Way A, for a pattern read as yes or no.** The neighbour test becomes a consumed character: `(?<![X])` becomes `(?:\A|[^X])`, `(?![X])` becomes `(?:[^X]|\z)`, `(?=[X]|$)` becomes a group that consumes. A match exists in one form exactly when it exists in the other, provided the assertion tests one character and stands at an edge of the pattern or of one alternative; where the match lies is not read. An assertion inside a pattern is first folded into the part beside it (`_LAST_ARG_RE`: the lookbehind into the class before it), and the rewritten pattern is proven like any other.
- **Way B, for a pattern whose spans or groups are read.** The pattern without the assertion finds a candidate, code tests the neighbour or the excluded words, and after a failed test the search goes on one character after the candidate's start. That is Python's result only when no shorter match at the same start could pass the test; where the part before the assertion can vary in length, the code first tries the shorter candidates at that start. These conditions are for the brief of step 3.3; the differential run is the proof either way.
- **Way C, a scanner written by hand**, for the one pattern with backreferences and a conditional.

Each is checked three times: by the differential run of step 3.3 on its own inputs, by its rule's fixtures through the conformance run, and by a planted break (the assertion dropped) that both must catch. The here-document scanner reproduces the pattern as it behaves, including what the shell would read otherwise: the port changes no verdict.

**The other 76 patterns** have a direct form in the `regex` crate, but four things do not mean the same and get a written translation rule, proven by the same run. `$` without the multi-line flag also matches before a final newline in Python and only at the very end in the crate. `\Z` is written `\z`. `\s` in Python also holds U+001C to U+001F, and `\S` leaves them out. `\w`, `\d`, `\b` and case-insensitive matching follow each engine's own Unicode tables, which already differ between Python 3.9 and 3.13; the run over every code point shows where, and each difference is removed or listed (section 7, line 4).

**Beyond patterns.** Python text can hold a lone surrogate from a JSON escape and Rust text cannot; Python integers have no limit. Where the Rust program cannot hold an input, it denies: a deny is the one answer that is never weaker than the Python guard's.

## 5. Where each place builds, and how a hook fails closed

One rule for all: `tools/rs/build.sh` is the only way to build. It finds a `cargo` whose `rustc` reports exactly the version in `tools/rs/toolchain` and refuses any other. It hashes `vendor/` and refuses when a file differs from `vendor.sha256`. It builds with `--offline --locked` from `vendor/`, under a lock, and puts the program at `tools/rs/bin/guard` with one rename, so a hook never reads a half-written file. It downloads nothing and installs nothing.

| Place | Toolchain | Who builds, when | State |
|---|---|---|---|
| The owner's Mac | the installed 1.100.0, called by its path and not through the `rustup` proxy; the pin is this version, so nothing is installed | `build.sh --if-stale` at session start and after `git` moves the tree; a session or the owner by one line otherwise | proven in 3.2 and 3.7 |
| The box | in the image, from a base pinned by digest | `box.py`, in a container, once per judge commit; a session in a box builds its own work with `build.sh` | proven in 3.2c |
| CI | installed by the job at the pinned version | the job `rust`, on every pull request | proven in 3.2b |
| Copilot cloud agent | installed by its setup steps | the setup steps, before the agent starts | written in 3.2b; proven only when someone runs it once (probe j); until then named as not served |
| The work machine | the owner's answer (section 7, line 14) | `build.sh`, run by him or at session start | open; it gates step 3.9 |

**Fails closed, two checks.** The launcher is a few lines of `sh` in the repository: when `tools/rs/bin/guard` is missing or cannot run, it prints the deny answer both harnesses read, exits 2, and the reason names the build line. The program holds the digest of what it was built from: every file the build reads under `tools/rs/` outside `vendor/` (both manifests, the crate's source, `Cargo.lock`, the pin, `.cargo/config.toml`, `build.sh`) and `vendor.sha256`, which stands for the vendored crates. It computes that digest again from the tree on each call; on a difference it denies and names the build line. `vendor/` itself is not hashed on each call: `build.sh` checks it against `vendor.sha256` before every build, and CI proves the committed folder. Named gap: a vendored file changed in the working tree after the last build is not seen until the next build, which refuses it. If the digest costs more than 3 ms (probe f), the fallback is a comparison of file times in the launcher.

**No deadlock.** A guard that denies every call would also deny the call that builds it. So the build is started outside the pre-tool hook: at session start, by the two `git` hooks, and by the owner with one line in his terminal. In a box the judge is read-only and built before the session starts.

**The guard's source is edited in a tree that does not judge the session.** That is a worktree, for a session started in the main checkout, or a box. A session that edits `tools/rs/` in its own project tree is denied from its next call on, the build call included, and only the owner's line in his terminal lets it go on; it is then judged by the code it has just written, as a session that edits `guard.py` in its project tree is today. From L on that edit asks first (`guard-config`). The steps of this plan are built in worktrees and boxes, so none of them meets this stop.

**What the decision log gains.** Each line of the Rust program gains one field, `build`, the digest above, so a recorded decision points at the source its program was built from. The comparisons of this plan leave that field out, since the Python guard writes none.

## 6. The shadow period, the switch, the deletion

- **Shadow.** From the merge of L both programs judge every `pre` call on the host and in a box, side by side and inside one budget of 3.5 s, so the hook stays below the 5 s cut of both wirings. The Python guard is the authority and drives the shadow. A disagreement is any difference in exit code, answer or log line (without its time and the field `build`), or a shadow that is late, missing or stale. On one, the call gets the stricter of the two answers and never less than the authority's: a deny if either denies, else an ask that names both (a deny in a box, by its table). A record with the redacted event is written under the telemetry folder, the authority's log line names the shadow's digest and says whether the two agreed (the field `shadow`), and the period's counts start again. Only the authority writes to `decisions.jsonl`. In CI a disagreement on the corpus or the pending list is a red job.
- **The switch (M) needs all five.** (1) 14 days and 5,000 live calls judged by both with no disagreement, at one source digest of the Rust program; a new digest starts the count again. That digest is the one at the head of M, which changes no file that enters it. (2) At the head of M: the conformance run with no pending case, the differential run and the 45-day replay, all equal. (3) The Mac, the box and CI have each built the program from source and passed the corpus there; the cloud agent and the work machine have his recorded answer. (4) The Rust hook's median on the Mac is at most 15 ms for the event of section 1, the staleness check included. (5) No listed divergence without his word.
- **After the switch** the Rust program is the authority and drives the Python guard as its shadow, under the same rules, for 14 days and 5,000 calls. Going back is the revert of one commit.
- **The Python guard is deleted in N**, at the earliest 28 days after L's merge, when the second period is clean and act 19 is recorded. If his answer is that a machine he uses cannot build, N does not delete: the Python guard stays in the kit for such machines, the conformance run keeps the two equal, and that outcome is recorded with its cost (each rule change twice).

## 7. Decisions taken in this plan

Each line is the owner's to strike; where two ways exist, both are named.

1. **All Rust lives in one workspace under `tools/rs/`.** Nothing at the repository's root: the kit is copied into task repositories, and a root `Cargo.toml` would collide with a target's own.
2. **Three crates and what they pull in: `regex`, `serde_json`, `sha2`.** No other; a new one later is a decision line. The list with licences is reviewed in 3.2. Alternatives: `fancy-regex` or `pcre2` keep the 14 patterns as written, but bring back backtracking, the reason for the kill at 3.5 s; a SHA-256 written by hand saves crates and puts own hash code into a control.
3. **The 14 patterns are carried by hand in three ways** (section 4).
4. **Equal means byte for byte**: exit code, standard output, the deny reason and the log line without its time and the field `build`. A divergence is allowed only where the Rust program cannot hold the input; it is then a deny, never weaker than the Python guard's answer, and each is listed with his word. Alternative: equal verdicts only; cheaper, and every reason text is then judged by eye.
5. **The pin is a version in a plain file, and it is 1.100.0**, the compiler on his Mac today, so the host needs no install. The wrapper compares and refuses. Alternative: `rust-toolchain.toml`, which the `rustup` proxy may answer with a download on the host (probe c), plus his one `rustup toolchain install` per pin. Named: when he updates his `stable`, `build.sh` refuses until the pin moves in a pull request or he installs 1.100.0 beside it.
6. **Building is not installing.** `build.sh` is offline, reads only the repository and writes only inside the clone, so a session, the session-start hook and two `git` hooks may run it. Every other call of `cargo`, `rustup` or `rustc` asks on the host (step 3.2). Alternative: only he builds, one line after every pull that moves the guard's source. Named: the built program then runs as his user on every tool call, as `guard.py` does today.
7. **Missing is the launcher's deny, stale is the program's deny** (section 5). The digest computed on each call leaves `vendor/` to the build and to CI, a named gap.
8. **The shadow period is 14 days and 5,000 calls, twice** (section 6). Shorter is his to say. For scale: the replay for guard 0.12.0 held 24,438 recorded calls of 45 days (`DECISIONS.md`), about 540 a day.
9. **The owner merges what changes which program a hook runs: L, M and N.** Alternative: the session merges L and N after his `/approve`, as it merges a rule change; two pasted lines fewer for him, and the wiring of the judge then changes without his own hand.
10. **Until the shadow starts `tools/rs/` is not a `guard-config` path.** No hook runs anything from it before L, so boxes build it and the host does not prompt on each edit. From L on it is guarded like `tools/guard/`, the built program and `vendor.sha256` included: the shadow's clean count gates the switch, so the shadowed program must not be replaceable without an ask. In the shadow period the call gets the stricter of the two answers, so a wrong Rust program can add asks and denies and can take none away.
11. **The box image carries the toolchain**, and the judge's program is built per judge commit. Alternative: build it on the host and mount it; impossible, since the host is macOS and the box Linux.
12. **One CI job under the existing check `ci`**, so the ruleset of Phase 2 needs no change. Both workflow files of the port sit in one pull request, C, since each workflow change is his to push and merge.
13. **The Copilot cloud agent is written for and not proven.** The setup file ships; until a run shows the hook finds the program, the documents say the cloud agent is not served, and the launcher denies there.
14. **The work machine decides the deletion.** The question for him: can it hold `rustup` and one pinned toolchain, and on Windows the build tools the compiler needs? Default until he answers: the Python guard is not deleted.
15. **Python stays** for the conformance runner, for every tool not yet ported and in CI.
16. **The other tools are sketched, not approved.** Items filed now would freeze guesses; each group's plan comes with the guard's measured cost per ported line and the answer on HTTPS.
17. **Through both periods the Rust program reports the Python guard's version** and its own source digest, since the two answers are compared byte for byte. It becomes guard 1.0.0 in N.

## 9. Error paths and edge cases

- **Phase 2 is not delivered as planned.** G0 reads what is there. Without the App identity the merges fall back to what holds then; without guard 0.13.0 the port starts from 0.12.2 and its figures stand.
- **Probe (a) fails**, the offline build needs the network: the phase stops, since building from vendored crates is his decision; the question returns to him.
- **Probe (e) fails**, a pattern is too large for the crate: the bounded gap is carried by way B, a search for the first word and a scan of at most 2,000 characters.
- **Probe (d) shows a cold build that outlasts the session-start hook:** the hook starts the build and does not wait; until the program is in place every call is denied, and the reason says a build is running.
- **Probe (i) shows that VS Code runs a call when its hook command cannot start:** the launcher is then the one piece that must always start there, the documents say so, and a machine without `sh` is not served (last line).
- **Probe (g) fails**, a case cannot be reproduced through the command line: it stays a Python test until its rule is ported, becomes a Rust test then, and is counted in the record.
- **A build is running while a hook fires:** the old program is in place until the rename; if it is stale it denies, and the next call finds the new one.
- **Two sessions build at once:** the lock; the second waits and finds the work done.
- **A session started in a worktree** has that tree as its project and builds its own program at session start; the cold build's time is probe (d).
- **The tree moves under a running session** (a pull): the `post-merge` hook builds inside the same call. If it fails, every later call is denied and the reason names the one line; the owner runs it.
- **The shadow is late, missing or stale:** a disagreement (section 6). The call gets at least an ask, and the authority's own answer is never lost.
- **A disagreement in the shadow period that is the Python guard's defect:** it is fixed in Python first, with a fixture, and the golden file follows; the Rust program is never the reference before the switch.
- **A vendored crate gets a security advisory:** a pull request moves the lock and `vendor/` together, built in a container; CI's comparison proves the new folder.
- **The work machine has no `sh`** (Windows without Git Bash): named with act 19; the launcher then needs a second form, which this plan does not build.

## 13. What an auditor gains, and does not

- **Gains.** Validation evidence for the port as a like-for-like replacement of a validated control: the corpus and its golden answers, the differential record, the planted-break lists, the replay and two shadow reports, each tied to a commit. Build provenance: the source and every dependency are in the repository under review, the lock file holds each crate's checksum, CI proves `vendor/` equals what the registry serves for that lock, the compiler is one named version, and no binary crosses a machine. Each logged decision names the digest of the source its program was built from. The requirement-to-check table (`docs/RULES.md`) keeps its rows.
- **Does not gain.** The compiler is a downloaded binary, trusted as the Python interpreter is today. On the host a session runs as the owner's user and can overwrite the built program, as it can edit `guard.py` today; from L on `guard-config` asks for a tool call that does so, and the residual of the parent plan (D6) stands: a session can write files in ways the guard does not read. `build.sh` accepts a vendored file changed together with `vendor.sha256`; on the host that edit asks from L on, and in a pull request CI's comparison with the registry fails. A vendored file changed in a working tree after the last build is not seen until the next build. Equal answers on recorded inputs do not show equal answers on every input; the differential inputs are generated, not exhaustive. The crates are read by their list and licences, not line by line. Author and reviewer are one model family.
